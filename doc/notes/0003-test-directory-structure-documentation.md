## 🔗 目录间关系和边界

### 明确的边界
- **lexer/** ↔ **parser/**: 词法分析输出 → 语法分析输入
- **parser/** ↔ **semantic/**: 语法树 → 语义验证
- **semantic/** ↔ **codegen/**: 验证后AST → 代码生成

### 可能的重叠区域
需要注意以下边界，避免测试重复：

#### lexer/ vs core/
- **lexer/**: 纯词法分析功能
- **core/**: 词法分析在整体编译流程中的表现

#### semantic/ vs parser/
- **parser/**: 语法结构的正确性
- **semantic/**: 语法结构的语义有效性

#### integration_extended/ vs 其他目录
- **其他目录**: 单一功能测试
- **integration_extended/**: 跨功能综合测试

## 🎯 测试组织原则

### 1. 单一职责原则
每个目录专注于特定的编译器组件或功能领域

### 2. 逐层验证原则
从基础组件(lexer)到高级功能(integration)的层次化测试

### 3. 明确边界原则
避免功能重叠，确保每个测试都有明确的归属

### 4. 可维护性原则
每个目录的测试数量适中，便于维护和修改

## 🔧 使用指南

### 添加新测试
1. **确定测试类型**: 根据功能确定应归属的目录
2. **检查现有测试**: 避免重复测试相同功能
3. **遵循命名约定**: 使用清晰的测试名称
4. **更新文档**: 在相应目录README中记录

### 修改现有测试
1. **定位正确目录**: 根据功能找到对应的测试目录
2. **理解测试边界**: 确保修改不会影响其他目录的测试
3. **保持一致性**: 遵循目录内的测试风格

### 重构测试结构
1. **评估影响范围**: 了解跨目录的依赖关系
2. **渐进式修改**: 避免大规模同时修改多个目录
3. **验证完整性**: 确保重构后所有功能都被覆盖
