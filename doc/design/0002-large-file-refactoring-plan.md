### 重构策略

#### 方案A：按韵组类型分离（推荐）
```
src/poetry/core/
├── rhyme_groups/
│   ├── an_rhyme_data.ml     # 安韵组数据
│   ├── si_rhyme_data.ml     # 思韵组数据
│   ├── tian_rhyme_data.ml   # 天韵组数据
│   ├── wang_rhyme_data.ml   # 望韵组数据
│   └── qu_rhyme_data.ml     # 去韵组数据
├── rhyme_data_consolidator.ml  # 数据整合器
└── rhyme_core_api.ml        # 统一API接口
```

#### 方案B：按功能模块分离
```
src/poetry/core/
├── data/
│   ├── rhyme_character_data.ml  # 字符数据
│   ├── rhyme_group_data.ml      # 韵组数据  
│   └── rhyme_statistics.ml      # 统计数据
├── utils/
│   ├── rhyme_data_helpers.ml    # 辅助函数
│   └── rhyme_performance.ml     # 性能优化
└── rhyme_core_api.ml            # 统一API
```

## 预期效果

### 可维护性提升
- **模块职责**: 每个韵组文件只负责特定韵组的数据
- **代码理解**: 开发者可以快速定位到具体韵组的实现
- **修改影响**: 单个韵组的修改不影响其他韵组

### 开发效率
- **并行开发**: 多人可以同时修改不同韵组而不产生冲突
- **编译速度**: 增量编译只重新编译修改的韵组
- **测试效率**: 可以针对单个韵组编写独立测试

### 技术指标
- **文件数量**: 1个728行文件 → 5-8个100-150行文件
- **复杂度**: 从"过高"降低到"适中"
- **维护成本**: 估计降低40-60%

## 风险和缓解措施

### 主要风险
1. **编译依赖**: 模块拆分可能导致循环依赖
2. **API兼容**: 外部调用者可能需要更新引用
3. **性能影响**: 数据分离可能影响运行时性能

### 缓解措施
1. **渐进式重构**: 逐步拆分，保持每步都能编译
2. **兼容性层**: 维持原有API，逐步迁移
3. **性能测试**: 重构前后进行性能基准测试
