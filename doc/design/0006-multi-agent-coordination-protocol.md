# 多代理协作协调协议 - 防止重复工作和规划泛滥

**Author: Oscar, Agent Coordination Facilitator**  
**日期**: 2025年7月31日  
**版本**: 1.0  

## 🎯 协议目标

基于骆言项目近期出现的重复战略规划问题（Issues #1830, #1831, #1832, #1833），本协议旨在建立清晰的多代理协作机制，防止资源浪费和工作重复。

## 📋 核心原则

### 1. 单一真相源原则
- **战略规划**：同一时期只能有一个活跃的综合战略规划Issue
- **技术实施**：每个具体技术问题只能有一个主要负责代理
- **文档管理**：同类文档合并管理，避免内容重复

### 2. 执行优先原则
- **规划限制**：避免过度规划，专注技术实施
- **进展导向**：以实际代码改进和问题解决为评判标准
- **时间控制**：战略规划讨论不超过2周，剩余时间用于执行

### 3. 责任明确原则
- **主责代理**：每个任务必须指定主要负责代理
- **协作边界**：明确代理间的职责边界和协作接口
- **质量保证**：建立跨代理的质量审查机制

## 🔄 工作流程规范

### 阶段1: 任务规划 (最多2周)
1. **需求识别**: 由项目维护者或Issue提出者明确需求
2. **重复检查**: 强制检查是否存在相同或相似的活跃Issue
3. **责任分配**: 指定主责代理和协作代理
4. **时间边界**: 设定明确的完成时间和里程碑

### 阶段2: 技术实施 (主要阶段)
1. **进展跟踪**: 每周在指定Issue中更新具体进展
2. **质量审查**: 关键变更需要至少2个代理审查
3. **问题升级**: 遇到阻塞问题立即在Issue中报告
4. **协作沟通**: 使用GitHub讨论，避免私下决策

### 阶段3: 成果验收
1. **功能验证**: 确保所有功能需求得到满足
2. **质量检查**: 测试覆盖率不得下降，性能不得回退  
3. **文档更新**: 同步更新相关技术文档
4. **经验总结**: 记录成功模式和改进建议

## 🚨 防重复机制

### 1. Issue创建前检查清单
- [ ] 检查现有开放Issues是否包含相同内容
- [ ] 验证是否属于已有Issue的子任务
- [ ] 确认时机是否合适（避免在实施期创建新规划）
- [ ] 明确本Issue的独特价值和必要性

### 2. 强制等待期
- **战略规划**: 新的综合战略规划Issue至少间隔3个月
- **重大重构**: 大型重构计划至少间隔1个月
- **工具开发**: 新工具开发需要先检查现有工具覆盖度

### 3. 自动化检测
- 建立关键词匹配系统，检测潜在重复内容
- PR和Issue模板包含重复检查提醒
- 定期审查（每月）识别和整合相似工作

## 📊 质量保证机制

### 技术质量标准
- **测试覆盖率**: 维持当前72.53%水平，核心模块达80%
- **性能基准**: 建立并维护编译性能基准
- **代码审查**: 所有核心代码变更需要跨代理审查
- **文档同步**: 技术变更必须同步更新文档

### 协作质量标准
- **沟通透明**: 所有重要决策在GitHub上公开讨论
- **进展汇报**: 每周五在相关Issue中更新工作进展
- **冲突解决**: 意见分歧在24小时内提交给项目维护者
- **知识共享**: 重要技术发现及时分享给相关代理

## ⚡ 紧急处理机制

### 高优先级情况
1. **编译错误**: 影响主分支编译的问题立即处理
2. **数据一致性**: 项目指标严重偏差立即修复
3. **CI失败**: 持续集成失败超过4小时立即介入
4. **安全问题**: 任何安全相关问题最高优先级

### 冲突解决流程
1. **识别冲突**: 任何代理发现工作重复或冲突立即报告
2. **快速评估**: 24小时内评估影响和解决方案
3. **协调决策**: 由Oscar协调相关代理达成一致
4. **最终裁决**: 无法达成一致时由项目维护者@UltimatePea决定
