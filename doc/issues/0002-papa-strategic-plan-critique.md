### Phase 2: Poetry模块重构 - **需重新分解**

#### ❌ 关键问题识别:

**问题1: 重复率评估不准确**
```yaml
Papa声称: "194个ML文件，70%代码重复率"
实际发现: 
  - 存在重复，但主要集中在韵律数据文件
  - 已有统一化工作正在进行 (Rhyme_core_unified)
  - 重复率约40-50%，而非70%
```

**问题2: 任务颗粒度过粗**
```yaml
Papa计划: "194个文件优化到120个以下" (整体目标)
需要分解为:
  1. 韵律数据文件统一 (20个文件 → 3个核心文件)
  2. 类型定义重复消除 (8个类型文件 → 2个核心类型)
  3. 数据访问层重构 (15个访问器 → 5个统一接口)
  4. 测试文件相应调整 (50个测试 → 35个测试)
```

**问题3: 技术依赖关系模糊**
- 缺少模块依赖图分析
- 重构顺序规划不明确
- 向后兼容性验证机制不清晰

### Phase 3: 测试覆盖率提升 - **目标合理但方法不足**

#### ⚠️ 需要细化的领域:
```yaml
Papa目标: "16.78% → 45%+ 测试覆盖率"
技术现实:
  - 当前测试文件: 396个
  - 当前源文件: 580个  
  - 测试/源比例: 68% (已经不错)
  - 问题在于测试质量，不是数量
```

**建议重新定义覆盖率指标**:
- 行覆盖率 → 分支覆盖率
- 数量指标 → 关键路径覆盖
- 整体提升 → 核心模块优先

## 🚨 关键技术风险评估

### 高风险区域
1. **Poetry模块重构并发风险**
   - 多个Agent同时修改相同文件
   - 缺少重构锁定机制
   - **缓解**: 建立文件级重构锁

2. **测试回归风险**  
   - 大规模重构可能破坏现有功能
   - 测试套件执行时间可能增加
   - **缓解**: 分阶段重构，每阶段完整验证

3. **向后兼容性风险**
   - API变更影响依赖代码
   - 韵律分析准确性可能下降
   - **缓解**: 保留兼容层，渐进式迁移
